# HFS+ in Executor

Read-only HFS Plus volumes for Executor: disk images holding an HFS+
volume (bare `H+`/`HX`, inside an HFS wrapper, inside an Apple partition
map or not) mount, and their files open as on Mac OS 8.1–9.

## The reader

`src/executor/romlib/hfs/plus/`, the `executor_hfsplus` library: host
code, no guest types, written from TN1150 ("HFS Plus Volume Format") and
TN1189 (partitions). The File Manager's volume, the System sideload and
`hfsplus_dump` use it.

- `image.h`: what it reads from, at 64-bit offsets (`pread`; in the
  browser the same call reaches WORKERFS/OVERLAYFS files). Executor's old
  disk I/O (`ROMlib_readwrite`) takes 32-bit offsets.
- `reader.h`: `volumeStarts` (every `Apple_HFS`/`Apple_HFSX` partition of
  an Apple partition map, else offset 0), `isHFSPlus`, `Reader::open` (a
  bare header or the HFS wrapper's embedded volume:
  `drAlBlSt * 512 + drEmbedExtent.startBlock * drAlBlkSiz`). B-trees with a
  64-node cache; catalog lookups by (parent, name) and by CNID (thread
  records); `childAt` keeps a cursor so indexed enumeration (PBGetCatInfo's
  `ioFDirIndex` 1, 2, 3...) costs a step per call; forks through their 8
  extents and then the extents overflow B-tree; hard links (`hlnk`/`hfs+`)
  resolved to `HFS+ Private Data:iNode<n>`. HFSX's binary order when the
  catalog says so (`keyCompareType` 0xBC). The journal is not replayed
  (classic volumes have none; a journaled volume mounts read-only as
  written).
- `unicode.h`: TN1150's `FastUnicodeCompare`; MacRoman ↔ decomposed
  Unicode; the classic File Manager's short names.

### Short names (Mac OS 9.0.4)

What the HFS API (31 MacRoman characters) sees of an HFS+ name, observed
on Mac OS 9.0.4 (`tests/guest/hfsplus/oracle-9.0.4/longnames.txt`, made by
`MakeLongNames` through `FSCreateFileUnicode`, reading back the FSSpecs):

- A name with a MacRoman form of 31 characters or fewer is that form
  (decomposed accents composed again: `Short Café.txt`).
- Otherwise: the MacRoman form cut so that `#` + the CNID in upper-case hex
  + the extension fit in 31: `This is a file with a ra#16.txt`.
- The extension is the last `.` and what follows, kept when 2 to 6
  characters long (`.abcde` kept, `.abcdef` not; a trailing `.` alone is
  not one; `.A leading dot...` has none).
- Characters with no MacRoman form become `?`, one per UTF-16 code unit
  that doesn't compose (Greek `ά` stored as α + U+0301 is `??`), and the
  name is shortened that way even when short: `Greek ???#1C.txt`. A `:` in
  the Unicode name is such a character (`Colon?in a name#2E`); `/` is kept.
- The classic File Manager opens an item by its short name (FSpOpenDF on
  each returned FSSpec worked).
- Names collide case-insensitively (`case test file.txt` after
  `Case Test FILE.txt`: dupFNErr).
- 9.0.4's Finder shows the short names and sorts by them.
- `PBHGetVInfo` reports `ioVSigWord` `'BD'` for an HFS+ volume.

### Tables (`unicode_tables.h`)

Generated by `tools/hfsplus/gen_tables.py` from published data:

- The case-folding table: TN1150 gives the algorithm and the table's
  layout, but its data only as a download. Derived from Unicode 2.1.2's
  `UnicodeData.txt`: U+0000 → 0xFFFF; Unicode 2.0's ignorable formatting
  characters (U+200C–200F, U+202A–202E, U+206A–206F, U+FEFF) → 0; a
  character with a canonical decomposition unchanged (never stored); an
  Lu/Lt/Nl character → its lowercase mapping; the rest unchanged.
  Identical to TN1150's table (as hfsfuse carries it) for all 65536 code
  points (`--check-casefold`).
- MacRoman: Apple's `ROMAN.TXT`, each character fully decomposed by Unicode
  2.1's canonical decompositions but for U+2000–2FFF and U+F900–FAFF
  (TN1150: not decomposed). The 52 decomposed MacRoman characters all
  appear in TN1150's decomposition table (`--check-decomposition`).

## Tests

- `executor.hfsplus_reader` (`tests/test_hfsplus_reader.py`): `hfsplus_dump`
  against hfsfuse's `hfsdump` (`~/storage/hfsplus-recon/src/hfsfuse`; skip
  without it): every folder's listing, each item's CNID, kind, type,
  creator, fork sizes and bytes; the long-name fixture's short names
  against 9.0.4's. Images: the fixtures in
  `src/executor/tests/fixtures/hfsplus` (gzipped: `longnames.img`, made on
  9.0.4; `blank-64m.img`, `blank-wrapped-64m.img` from `mkfs.hfsplus`) and,
  where present, `~/storage/hfsplus-recon/images/{carbonlib-1.6,guest-written}.img`.
  By hand, with `--sample`, the two partitioned HFS+ CDs in the assets
  repo (ADC Seed CD April 2001: partition map + HFS wrapper, 7920 items;
  CodeWarrior 8 Pro: partition map, Mac OS X-written, 8270 items) matched
  in full; the reader's tree through the partition map equals its tree of
  the partition alone. hfsdump itself reads no partition map and loops
  listing an empty folder (the test times it out and compares valences).
- `executor.HFSPlusUnicode.*` (`src/executor/tests/hfsplus_unicode.cpp`):
  the order, MacRoman round trips, decomposition, the 9.0.4 short names.

Not covered by any image yet: hard links (none of the images has one),
HFSX, journaled volumes, files over 2 GB.

## Making fixtures

`tests/guest/hfsplus/`: `MakeLongNames` (68k, built with
`tools/mpw/mpw build tests/guest/hfsplus -o tests/guest/hfsplus` against
Universal Interfaces 3.3.2, docs/MPW.md) and `make_fixture.py`, which runs
it on Mac OS 9.0.4 (mame-ppc) against a blank volume and opens the result
in the Finder. Blank volumes: `mkfs.hfsplus [-w] -v NAME` in an Ubuntu
container (`hfsprogs`; Debian 13 and this kernel have no HFS+ writer).
